## 1. A mutation can produce an identical prompt, and still cost a full node

**Observed** — real Gemini run, `results2.json`, generation 0.

`node1` records two applied mutations in its changelog and its prompt is
byte-identical to the seed:

```
node1 | prompt: "Answer the question."
      changelog: ["MUTATION: [Removal] Remove overly cautious constraints that prevent th…",
                  "MUTATION: [Structure] Convert paragraphs to bullet checklists"]
node0 | prompt: "Answer the question."          <- the seed itself
      changelog: ["MUTATION: Seed prompt (baseline)"]
```

Both scored identically (0.67). The engine paid for the proposal call, the apply
call, and three candidate evaluations to re-measure a prompt it had already
measured — 25% of that generation.

Nothing compares the applied prompt against its input. A no-op mutation is
indistinguishable from a real one in the changelog, the graph and the report.

**Fix direction:** after applying, if the result equals the parent prompt,
either retry the operator or mark the node so it is not evaluated again.

## 2. The mutation INSTRUCTION becomes the prompt

**Observed** — same run, same generation.

```
node3 | prompt: "Rewrite the role/identity statement to better align with the actual
                 task requirements: You…"
```

The service model echoed the instruction instead of performing it, and the
engine adopted that text as a candidate prompt and evaluated it.

Same class, seen earlier with a plugin provider: when the service model returned
the mutation proposal JSON where the rewritten prompt belonged, the engine made
`[{"label":"ADD","edit":"append the token ALPHA"}]` the **champion prompt** and
reported the run successful.

Nothing validates that what comes back from the service model is a prompt rather
than the model's own reasoning about a prompt. A weaker or overloaded service
model does this routinely.

**Fix direction:** a sanity check on the applied prompt — rejects text that is
JSON, that reproduces the operator instruction, or that contains the
`<<< >>>` scaffolding — and retry rather than adopt.

## 7. Desktop: the holdout tile is blank in every failure case

`apps/desktop/src/components/Footer.tsx:187`

```jsx
{evaluation.holdout?.seed && evaluation.holdout?.champion && ( … )}
```

Renders only when **both** halves scored. Budget stop, no champion, manual stop,
circuit-breaker abort, or one half completing before a stop all render nothing —
so "no tile" is ambiguous between *no holdout configured* and *configured but it
did not run*. The CLI report distinguishes these (`skipped: 'no-champion'`,
`'budget'`, `'error'`, …); the UI does not.

The CLI report marks contaminated holdout rows and suppresses the delta callout.
The desktop shows the bare numbers, so `0.00 → 5.00` produced by a failed judge
is indistinguishable from a measured result.
